# PAMG Baseline Model — Technical Reference (v1.0)

Reference specification for implementers (human or AI agent) building against the PAMG baseline algorithm. This document is a normative restructuring of the source material — it is not a narrative or a learning guide; every claim below is tagged with its provenance so a consuming agent can weight it correctly.

## 1. System architecture

```
Play/Stop → 1. Clock (Tempo, Size, Grain) → indexed Count Loop
                    │
        ┌───────────┼──────────────┐
        ▼           ▼              ▼
   2. Melody     3. Harmony    4. Percussion
   Agent (MA)    Agent (HA)    Agent (PA)
        │           │              │
        └─────┬─────┘              │
              ▼                    │
      5. Orchestration Agent (OA)   │
              │                    │
              ▼                    ▼
         MIDI port  ◄──────────────┘
```

| Agent | §-range | Output ovals | Terminal route |
|---|---|---|---|
| Melody Agent (MA) | 2.x | Pitch in harmony, Velocity, Duration | → 5. Orchestration Agent `[SPEC]` |
| Harmony Agent (HA) | 3.x | Harmony pitches, Velocity, Duration | → 5. Orchestration Agent `[SPEC]` |
| Percussion Agent (PA) | 4.x | Percussion pitches, Velocity | → **MIDI port directly** `[SPEC]` |
| Orchestration Agent (OA) | 5.x | MIDI stream (channels assigned) | → MIDI port |
| Multi-Parameter Preset Interpolator (MPIC) | 6 | Interpolated parameter values | → all agents |
| Seeded Phrase Generator | 7 | Seed / Rhythm-Seed number | → all agents |

**Routing asymmetry (architecturally load-bearing, implement deliberately):** MA and HA's MIDI Event Construction stages (`2.6`, `3.5`) are captioned "to 5. Orchestration Agent." PA's MIDI Event Construction stage (`4.5`) is captioned "to MIDI port" — it does not pass through OA. Any implementation that routes all three agents through a shared orchestration/instrument-assignment layer deviates from the baseline; PA must have its own independent instrument-assignment path (see §4.3).

## 2. Data model

### 2.1 Onset / rhythm grid (shared structure, used by MA, HA, PA)

A per-loop table, one column per Count Loop index, populated top-down by the rhythm-generation stage of each agent:

```
Index          0   1   2   3   4   5   6   7   ...
Duration       2   0   3   0   0   1   0   1
Stacc./legato  L   —   L   —   S   —   L
```

`[FIG]` `0` in the Duration row = no onset at that index (filled by Add/Sub Filling, see §3.1). Non-zero = an onset, with its duration value and its derived `L`/`S` classification (§3.2).

Percussion uses the same index axis but one row per percussion voice instead of one shared Duration/Stacc-legato pair:

```
Index     0   1   2   3   4   5   6   7   ...
Snare     0   0   0   0   1   0   0   0
Kick      1   0   0   0   0   0   0   0
Toms      0   0   1   0   1   0   1   0
Cymbals   0   1   0   1   0   1   0   1
```
`[FIG]`

### 2.2 Chord dictionary

```
ChordDictionary : Map<(ChordSymbol, TensionLevel[1..12]), PitchClassSet>
```
`[SPEC]` Precomputed table, queried at runtime by `3.3.3. Chord Dictionary Query`. Not a curated chord list — it is generated by the tension algorithm (§4.2) applied to every chord symbol in the grammar (§4.1). Appendix C of S2 is the full printed table.

### 2.3 Chord pools

```
ChordPool[complexity_level] : Set<ChordSymbol>
```
`[SPEC]` Managed by `3.3.2.1. Chord Pools Manager` (Appendix B of S2). Higher `Cpx Prog` (Complexity Progression) values unlock access to higher-indexed pools. **Chord Pool #1 is distinguished at runtime** — it is the sole gate condition for the Seeded Phrase Generator (§7.1).

### 2.4 Seed state

```
SeedState {
  base_seed: int          // user-set
  current_seed: int        // broadcast to all agents
  rhythm_seed: int         // shares the same reseed mechanism as current_seed
}
```
`[SPEC]` Single shared state object; see §7.1 for the update rule.

## 3. Melody Agent (MA) — §2.x

### 3.1 Rhythm generation (`2.1`)

| Sub-stage | Function |
|---|---|
| `2.1.1` Beat and Moved list | Builds the base onset list from beat positions; "Moved" onsets are syncopation-shifted copies — this list is also consumed downstream by pitch contour generation (§3.3) and is shared with HA/PA to "emphasise the melody accents completely or partially" `[SPEC]` |
| `2.1.2` Add/Sub Filling | Additive/subtractive algorithm that subdivides/thins the onset grid (down through 8th/16th-note levels) |
| `2.1.3` Staccato/Legato duration | See §3.2 |

Fed by `2.5.2. Melody Change (Phrase change)`, which perturbs the rhythm stage on phrase boundaries, and by the shared `Count Loop`.

### 3.2 Staccato/legato classification algorithm

```
for each onset in onset_list:
    gap = distance_to_next_onset(onset)
    onset.articulation = STACCATO if gap <= threshold else LEGATO
```
`[SPEC]` (S2 §3.2.1) This is a **computed classification**, derived from inter-onset distance after rhythm generation completes — not an independently settable per-note switch. The exact threshold value is not given in either source `[INFER: implementation detail, not specified]`. Identical algorithm is reused verbatim by HA (§4, `3.1.3`) — S2 states this explicitly ("same as in Melody Staccato-legato").

No equivalent stage exists for PA — neither source lists a staccato/legato stage under `4.x`. Do not implement one for percussion voices.

**Articulation realization is sampler-dependent, not MIDI-generic:** staccato strings specifically are realized via sampler key-switches, described in S2 as "particular to the sampler/bank device" `[SPEC]` — not a property the generation algorithm itself encodes into the MIDI stream for all instrument families.

### 3.3 Pitch generation (`2.3`)

| Sub-stage | Function |
|---|---|
| `2.3.1` Note Stream Generation | `drunk` or `dcontour` mode, see below |
| `2.3.2` Transposition | Shifts pitch per `2.4 Shape Melody` and `2.5.1 Melody Change (Transp. change)` |
| `2.3.3` Harmony Filter | Filters generated pitches against the currently active harmony pitch-class set (supplied by HA) |

**Note stream generation modes** (both are modified versions of Max/MSP's `Drunk` object — random walk generator):

| Mode | Behavior |
|---|---|
| `drunk` `[SPEC]` | Standard drunk-walk behavior, **except the seed drives the sequence, not the range** — range is an independent parameter |
| `dcontour` (drunk-contour) `[SPEC]` | Uses drunk output to generate a pitch *contour* per loop; new onsets interpolate between the Moved List onsets from `2.1.1` |

Long-range shaping (`2.4 Shape Melody`) modifies pitch range across a window of **1/4 to 8 loops** using `depth` and `length` parameters, preserving local contour while adding directional drift. `[SPEC]`

Harmony Filter (`2.3.3`) output feeds the "Pitch in harmony" oval directly — confirms melody pitch output is always post-filtered against active harmony, never raw drunk-walk output. `[SPEC]`

### 3.4 Velocity generation (`2.2`)

Assigns velocities to onsets via a random-walk sequence, with accents placed on syncopated onsets. `[SPEC]`

### 3.5 MA parameter reference

| Parameter | Status | Maps to |
|---|---|---|
| `step` | `[SPEC]` | `2.3.1` drunk/dcontour step size |
| `range` | `[SPEC]` | `2.3.1` drunk/dcontour pitch range |
| `trans` | `[INFER]` | Likely `2.3.2 Transposition` / `2.5.1 Melody Change` |
| `velocity` | `[SPEC]` | `2.2 Velocity Generation MA` |
| `tac` (Tacet) | `[DEMO]`/`[INFER]` | Not named in S1/S2 text; owner's reading from GUI is a mute/silence control. Consistent with S2's stated exclusion of non-generative UI controls from Appendix A, but unverified against written spec. |
| `+/- notes` | `[SPEC]` | `2.1.2 Add/Sub Filling` |
| `Mv Even` / `Mv Odd` | `[SPEC]` | Even/odd syncopation-move split, §3.2.1 |
| `Orch +/-` | `[FIG]` | `{Orch +/- (MA)}` into OA `5.1.1` (see §6.1) |
| `Orch Range` | `[FIG]` | `{Range (MA)}` into OA `5.3` (see §6.1) |
| `Stacc/Legato` | `[SPEC]` | Computed output of `2.1.3`, see §3.2 — not a raw input |

## 4. Harmony Agent (HA) — §3.x

### 4.1 Chord grammar

Roman-numeral grammar with tiered modification classes `[FIG]`:

| Tier | Color | Meaning |
|---|---|---|
| Base | Yellow | Diatonic chords in the active major/minor scale |
| Mod tier 1 | Blue | Secondary dominant modifications (e.g. ii → V7/V) |
| Mod tier 1 | Green | Secondary subdominant modifications |
| Mod tier 2 | Purple | Chromatic tension-linked modifications — Neapolitan (N7), Italian+ (It+), French+ (Fr+); German+ (Ger+) is reclassified functionally as V7/♭II (hence blue, despite being an augmented-6th chord) |

`3.3.2. Harmonic Progression Selector` traverses this grammar, modeled after Cope's Augmented Transition Network approach but using Western-tonal transition probabilities rather than corpus-derived/learned transitions — no pre-composed pattern matching involved. `[SPEC]`

### 4.2 Tension mechanic — pitch-class-set construction

For any chord symbol, pitch classes are added across 12 ordered levels, same ordering logic for every chord (only the actual pitch-class values shift with root/quality):

| Levels | Addition | Worked example (I in C major) |
|---|---|---|
| 1–3 | Root triad (root, fifth, third) | 0, 7, 4 |
| 4–7 | Upper tertian extensions | 11, 2, 5, 9 |
| 8–10 | Borrowed parallel-minor tones | 3, 10, 8 |
| 11–12 | Chromatic dissonances | 6, 1 |

`[SPEC]` (S2 §3.2.5, Fig. 12) Tension is an index into this ordered list, not an independent dissonance scalar layered on top of a fixed chord.

**Voice-count interaction:** `voice ins` selects how many of the *currently unlocked* pitch classes (by tension level) actually sound, taking the most-recently-unlocked (most dissonant-so-far) first — i.e. the right-most N entries of the active prefix.

```
voiced_pitches(tension_level, voice_count) =
    last N of ordered_pitch_class_list[0 : tension_level]
    where N = voice_count
```

Worked examples (chord = I in C major): `tension=12, voice_ins=3` → `{8, 6, 1}`. `tension=7, voice_ins=3` → `{7, 11, 2}`. `[SPEC]`, worked example computed by compiler from S2 data.

### 4.3 Harmony sequence generation pipeline (`3.3`)

```
3.3.1 Switch Harmony
   → 3.3.2 Harmonic Progression Selector
        → 3.3.2.1 Chord Pools Manager  (reachable chords per Cpx Prog level)
        → 3.3.3.2 Bass Selector        (parallel bass-note process)
   → 3.3.3 Chord Dictionary Query      (retrieves pitch-class set)
        → 3.3.3.1 Post Filter          (fast-cut switch to new pitch sub-set)
   → 3.3.4 Chord Builder               (voices as block chord)
        ↔ 3.4 Harmony Change           (adjusts params on modulation/rhythm change)
   → 3.3.5 Arpeggiator                 (voices as broken/arpeggiated figure)
        ↔ 5.4 Send/receive flags (OA)  (bidirectional)
```
`[FIG]` `3.3.3.1 Post Filter` is a fast switching mechanism distinct from the gradual tension-level crossfade — described as enabling rapid switch to a new pitch subset. `[SPEC]`

**Chord Builder vs. Arpeggiator selection rule:**
- `[SPEC]` S2 §3.2.2: the arpeggiator is toggled on/off as part of phrase segmentation (tied to dominant/tonic entrances and "breakdown interludes").
- `[DEMO]` Observed directly: sweeping Tension toward its maximum (level 12) switches Harmony output from arpeggio to block chord; intermediate tension plays arpeggio.
- `[INFER]` These two observations are not contradictory — segmentation most plausibly gates *when* arpeggiation is permitted at all; tension level then decides block-vs-arpeggio *within* that window. A pure `tension == 12 → block chord` rule with no segmentation gate is a simplification, not the full confirmed behavior; it may produce chord blocks mid-phrase where the reference implementation would not. **Implementers should treat the exact combined rule as not fully specified** and validate against the demo footage directly rather than this document alone if precision matters.

### 4.4 Rhythm generation (`3.1`) and velocity (`3.2`)

Structurally identical to MA: `3.1.1 Accent/Beat Follower`, `3.1.2 Add/Sub Filling`, `3.1.3 Staccato/Legato Duration` (same algorithm as §3.2 above, reused verbatim per S2). `3.2 Velocity Generation HA` emphasizes chord onsets relative to the main accent list supplied by MA. `[SPEC]`

### 4.5 HA parameter reference

| Parameter | Status | Maps to |
|---|---|---|
| `Tension` | `[SPEC]` | §4.2, pitch-class-set level |
| `Complexity Progression` (`Cpx Prog`) | `[SPEC]` | Chord Pools Manager reach, §4.1/4.3 |
| `+/- Notes` | `[SPEC]` | `3.1.2`, shared algorithm with MA |
| `Acc/Beat` | `[SPEC]` | `3.1.1 Accent/Beat Follower` |
| `Vel ins` | `[INFER]` | Likely `3.2 Velocity Generation HA`; "ins" suffix unexplained in text |
| `Voice ins` | `[SPEC]` | §4.2 — exact term used in worked example |
| `Range ins` | `[INFER]` | Likely surfaces OA's `5.5 Instrument Ranges` in the HA panel; not literally named in running text |
| `Register ins` | `[DEMO]`/`[INFER]` | Owner's reading: "Registered Instruments." Architecturally plausible (HA needs to know current instrument assignment from OA to voice sensibly) but not named in S1/S2. |
| `Ins (Instrument) +/-` | `[FIG]` | `{Orch +/- (HA), velocity, voices, range}` into OA `5.1.2` |
| `Stacc/Legato` | `[SPEC]` | `3.1.3`, same algorithm as MA |
| `Move` | `[INFER]` | Likely the HA-side "Moved List" concept shared from rhythm generation; not separately named |

### 4.6 Project Harmony mode mapping

The demonstration UI exposes a Harmony Major/Minor control `[DEMO]`. This
project maps that discrete control through the four XY presets: Presets A and
C use `minor`, while Presets B and D use `major`. Mode changes are applied at
phrase boundaries, like other discrete preset values.

The project uses natural minor for `minor` mode: i minor, ii° diminished, III
major, iv minor, v minor, VI major, and VII major. This is an implementation
choice because the written PAMG sources do not specify the minor-mode scale
formula.

The current implementation also uses two local rules where the source is
underspecified: phrase segmentation gates arpeggiation and tension levels
4–10.5 select arpeggiation inside that window; the local arpeggio denominator
is `4 × grain`. A post-filter is authoritative: if it matches no active pitch
classes, Harmony emits no pitches or events.

## 5. Percussion Agent (PA) — §4.x

### 5.1 Rhythm generation (`4.1`)

`4.1.1 Accent/Beat Follower` and `4.1.2 Add/Sub Filling` reuse the same algorithms as MA/HA, applied independently per percussion voice (Snare, Kick, Toms, Cymbals) against the shared Count Loop index — see grid in §2.1. `[FIG]`

No staccato/legato stage exists for PA (see §3.2).

### 5.2 Velocity and ratchet

| Sub-stage | Function |
|---|---|
| `4.2` Velocity Generation | Accentuates specific percussion onsets `[SPEC]` |
| `4.3` Ratchet | Decides when/how fill-in rhythmic repetitions appear `[SPEC]` |
| (implicit) Change | Aligns percussion with chord changes `[SPEC]` |

### 5.3 Instrument layering — internal to PA, not OA-mediated

There is no `5.1`-equivalent add/subtract-instrument stage for percussion. Layering is simply however many of the four onset rows (§2.1) are simultaneously active at a given index — a direct output of per-voice rhythm generation, not a separate orchestration decision. `[SPEC]`/`[FIG]` Combined with the §1 routing asymmetry (PA's `4.5` goes straight to MIDI port), **percussion instrument management is architecturally self-contained**: it does not share OA's instrument-switching, range-management, or voice-assignment machinery.

### 5.4 PA parameter reference

| Parameter | Status | Maps to |
|---|---|---|
| `Vel Perc` | `[SPEC]` | `4.2 Velocity Generation` |
| `Acc/BeatP` | `[SPEC]` | `4.1.1 Accent/Beat Follower` |
| `+/- KS` (Kick/Snare) | `[DEMO]` | Confirmed as **one combined GUI control** over the Kick and Snare onset rows, which are independently generated at the algorithm level (§2.1 shows them as separate rows). Implement as one UI control driving two independent onset-generation calls with a shared delta — not a merged data structure. |
| `+/- Toms` | `[FIG]` | Toms row, onset grid |
| `+/- Cymb` | `[FIG]` | Cymbals row, onset grid |

## 6. Orchestration Agent (OA) — §5.x

### 6.1 Pipeline (MA and HA streams only — PA does not pass through OA)

```
2.6 MIDI Event Construction MA ──┐
3.5 MIDI Event Construction HA ──┤
                                  ▼
5.1.1 Add/subtract instruments (melody lines)   {Orch +/- (MA)}
5.1.2 Add/subtract instruments (assign voices)  {Orch +/- (HA), velocity, voices, range}
                                  ▼
5.2 Switch Instruments
                                  ▼
5.3 Range Melody lines   {Range (MA), Pitch Class List for Melody}
5.4 Send/receive flags  ↔ 3.3.5 Arpeggiator (HA)
                                  ▼
5.5 Instrument Ranges   {Inst. range1, Inst. range2, ...}
                                  ▼
MIDI stream (MA/HA, channels assigned) → MIDI port
```
`[FIG]` Neither MA nor HA decides its own instrumentation — both emit a content stream, and OA independently decides instrument count (`Orch +/-`), active instrument/switch state (`5.2`), and pitch range (`Orch Range` / `5.5`) as three separable decisions, not one combined knob.

### 6.2 Instrument palette constraint

Baseline model is scoped to four full-range orchestral families — **Strings, Piano, Woodwinds, Brass** — plus "cinematic percussion." `[SPEC]` Idiomatic restrictions: arpeggios avoided for Brass; only piano solo permits arpeggio rates down to 1/32 note value; staccato strings realized via sampler key-switches. Hard-coded in the baseline; author flags generalizing to other instrument sets as future work, not something the current algorithm does automatically.

## 7. Shared cross-agent mechanisms

### 7.1 Seeded Phrase Generator (§7, Fig. 7)

Single shared mechanism driving both pitch and rhythm reseeding (S2 §3.2.2: "This also applies to the Rhythm Seed"):

```
on_loop_tick():
    if current_chord_pool != ChordPool[1]:
        return  # Do Nothing — existing seed persists, gesture repeats verbatim
    new_value = seeded_random(base_seed, bound=seeded_phrase_length)
    current_seed = base_seed + new_value
    broadcast(current_seed, rhythm_seed)  # to all agents, same tick
```
`[SPEC]` Gate condition is specifically re-entry into **Chord Pool #1** (the lowest-complexity pool, §2.3) — not any chord change. Phrase repetition duration is therefore tied to harmonic cycling, not a fixed bar count.

**Terminology note:** neither S1 nor S2 uses the word "motif." The spec's own term is "Seeded Phrase." The functional effect — a melodic/rhythmic gesture that repeats until reseeded — matches informal "motif" usage, but implementers should use "Seeded Phrase" when cross-referencing the dissertation.

**Zero-seed behavior:** `[SPEC]` 0-seeded values disable the repeat-gesture gate entirely, producing continuously-varying, non-repeating output each tick — described in S1 as "improvisational passages."

### 7.2 Multi-Parameter Preset Interpolator (MPIC, §6, Fig. 6)

Four presets per agent, assigned to the four corners of an XY pad; pad position bilinearly interpolates across all parameters simultaneously. `[SPEC]` Distinct from both OA's instrument add/subtract mechanism (§6.1) and CBI's track-layering (§8.2) — all three reuse 2D/spatial framing in the source figures, which makes them easy to conflate; they are functionally unrelated.

## 8. Cross-cutting architectural notes

### 8.1 Routing asymmetry (restated as an implementation constraint)

Do not implement a single shared "instrument layer" abstraction across all three content agents. MA/HA instrument assignment is entirely OA-owned (§6.1); PA instrument/voice management is entirely internal to PA (§5.3) with no OA involvement and a direct MIDI-port output path. These are two independent code paths in the reference architecture, not one path with three callers.

### 8.2 "Layering" terminology disambiguation

The word "layering" appears in the sources for **three distinct, unrelated mechanisms** — do not merge them in implementation or documentation:

| Mechanism | Scope | Source |
|---|---|---|
| CBI "2D Transition through layering" | Adds/removes pre-recorded music *tracks* by player proximity to map corners (0–3 tracks/theme) | This is the **Clip-Based Implementation comparison baseline**, not PAMG itself. `[SPEC]` |
| OA instrument add/subtract (§6.1) | PAMG's actual MA/HA instrument-count mechanism | PAMG internal |
| PA per-voice onset activity (§5.3) | How many percussion rows are active per index | PAMG internal |
